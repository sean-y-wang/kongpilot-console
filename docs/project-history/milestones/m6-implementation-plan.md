# M6 开发者门户实施计划

本阶段在 M5 的真实部署验收通过后实施。使用同一工作流基础支持门户凭证申请；M11 在这一基础上增加多级、会签、定时和变更窗口。本文件是改动计划，不代表功能已经交付。

## 实施内容

1. 新增独立门户 React 应用，开发环境端口 8082。门户和管理控制台分别使用签名密钥、JWT issuer/audience、Cookie 名称、会话表和 CSRF 校验；开发者不会成为控制台用户。
2. 迁移 008 增加门户开发者、会话、应用、发布文档、页面、凭证记录，以及公共工作流、审批、步骤和事件。秘密按对象上下文加密，审批计划批准后不可改写，删除保留记录。
3. 门户提供注册、登录、应用、文档搜索、OpenAPI 展示、Markdown 页面、API Key 申请及授权查看。管理侧提供开发者审核、内容与外观、应用和审批列表。
4. 凭证申请由服务器生成 Consumer/凭证 ID 和密钥。审批重新校验当前开发者、应用、API、集群、工作区及审批人权限，使用受限服务器能力执行批准的精确步骤；集群保持原执行模式。
5. 创建、轮换和吊销复用实体、回收站、审计、物理锁和监控写入栅栏。未知结果保留原计划及回执，不生成第二个密钥。轮换和吊销二次确认，原凭证归档。
6. OpenAPI 不执行外部引用或任意代理请求，Markdown 禁止原始 HTML，文档及错误回显脱敏。门户身份不可调用控制台接口或读取其他开发者的应用与密钥。
7. Kong 1.5 的 API Key 是网关级凭证，不天然限定某个 API。每个应用与 API 的授权分别创建 Consumer、ACL 分组及 Key；先配置 Service 的 ACL 白名单，再配置 key-auth，最后发布门户元数据。发放前检查实际插件优先级及其他认证表面；不能证明其他 API 拒绝该 Key 时，拒绝发布或发放并给出修复说明。后续普通原生变更继续保护此边界。
8. 开发者注册处于待审核状态时不能登录。开发者的申请只使用控制台数据库中的已成功发布证明编译计划，不读取 Kong、不伪造控制台账号；实际审批执行由当前有效的控制台会话重新检查原生对象、权限和快照。
9. 原生批准能力与元数据批准能力分别使用私有活跃祖先和不可变步骤证明；客户端传来的工单 ID 不授予能力。元数据步骤只调用固定 SQL handler，保留空的原生 operation 关联，M6 不为普通 IAM 元数据操作增加审批旁路。

## 验证与交付

先运行迁移和权限/计划能力的单元与数据库验证，再由唯一部署器发布 M6。真实双集群验证注册→审核→应用→申请→另一管理员审批→Consumer/key-auth→代理认证，随后轮换和吊销并检查旧/新密钥实际状态。记录网络传播耗时，不把 Kong 的最终一致性描述为即时生效。

浏览器验证独立门户、控制台审批、文档和移动端。拒绝匿名、跨开发者、跨工作区、伪控制台 JWT、缺 CSRF、原始 HTML/外部引用和未批准执行。所有成功写入关联审计；凭证仅在仓库外临时 0600 引用中用于验证，完成截图和运行时扫描后清除。通过并提交 M6 后继续 M7，不再等待阶段确认。
